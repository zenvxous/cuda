# Лабораторная работа №1 — умножение блочных матриц

**Вариант: тип `double`, малая матрица `8×8`. Платформа: x86-64, SSE2.**

Перемножаются две матрицы, элементами которых являются матрицы меньшего размера,
тремя способами, после чего сравниваются время работы и результаты.

| Результат | Реализация | Файл | Ключи сборки |
|---|---|---|---|
| **C1** | скалярный код, **автовекторизация ВКЛ** | `src/multiply_scalar.cpp` | `-O3` |
| **C1** | **тот же** скалярный код, **автовекторизация ВЫКЛ** | `src/multiply_scalar.cpp` | `-O3 -fno-vectorize -fno-slp-vectorize` |
| **C2** | **ручная векторизация** SSE2 intrinsics | `src/multiply_simd.cpp` | `-O3 -msse2` |

---

## Быстрый старт

```sh
make          # сборка (Release)
make run      # прогон с настройками по умолчанию
make help     # список всех целей
```

Зависимостей нет, нужен только компилятор C++17 (clang или GCC — Makefile сам
подставляет нужные ключи отключения векторизации).

---

## Постановка задачи

Внешние матрицы `A[L×M]`, `B[M×N]`, `C[L×N]`; каждый **элемент** — плотная матрица
`8×8` типа `double`:

```
C[i][j] = сумма по k из ( A[i][k] × B[k][j] ),
```

где `A[i][k] × B[k][j]` — обычное умножение матриц `8×8`, а сумма — поэлементное
сложение матриц `8×8`.

При размерах по умолчанию (`L = M = N = 448`) это эквивалентно умножению двух
плотных матриц `3584×3584` элементов `double`: 92 GFLOP, около 490 МБ памяти.
Требование «время получения C1 от нескольких секунд» выполняется; если конкретная
машина окажется заметно быстрее, размер поднимается флагом `--size`.

---

## Хранение данных

Раскладка **блочно-непрерывная**: весь массив — один блок памяти, каждая малая
матрица лежит в нём целиком подряд, внутри неё элементы хранятся построчно:

```
элемент (r, c) блока (i, j)  ==  data[ ((i * cols + j) * 64) + r * 8 + c ]
```

```
        блок(0,0)      блок(0,1)      блок(0,2)         ...
     ┌──────────────┬──────────────┬──────────────┬──────
data │ 64 × double  │ 64 × double  │ 64 × double  │ ...
     └──────────────┴──────────────┴──────────────┴──────
       ↑ 512 байт     ↑ 512 байт
```

Это буквально соответствует формулировке задания («элементы матрицы — своя матрица
меньшего размера») и одновременно даёт последовательный доступ к памяти внутри блока.
Базовый адрес выровнен на 64 байта (`posix_memalign`), размер блока `8·8·8 = 512` байт
кратен 64, поэтому каждый блок тоже выровнен — используется выровненная загрузка
`_mm_load_pd`, а не `_mm_loadu_pd`.

---

## Порядок обхода и почему результаты совпадают ПОБИТОВО

Задание требует, чтобы C1 и C2 совпали **полностью**. Для `double` это означает
побитовое равенство, а оно достигается только при **одинаковом порядке операций
с плавающей точкой** (сложение вещественных чисел не ассоциативно). Обеспечено двумя
мерами.

### 1. Один и тот же порядок обхода i-k-j во всех трёх реализациях

```
C = 0
для i         (блочная строка)
  для k       (блочный индекс суммирования)
    для j     (блочный столбец)
      для r   (строка внутри блока)
        для k2  (столбец A / строка B внутри блока)
          для c (столбец внутри блока)   ← ЭТОТ цикл векторизуется
            C[i][j][r][c] += A[i][k][r][k2] * B[k][j][k2][c]
```

Для каждого конкретного элемента `C[i][j][r][c]` слагаемые набираются строго в порядке
возрастания `k`, затем `k2`. Этот порядок одинаков в скалярной и в SIMD-версии,
поэтому результаты обязаны совпасть бит в бит — что программа и проверяет
через `memcmp` по всему буферу.

Векторизуется внутренний цикл по `c`: его итерации независимы (разные элементы
результата), и каждая половина регистра `xmm` ведёт свою собственную сумму в том же
порядке, что и скаляр.

Порядок i-k-j выбран ещё и из соображений производительности:

* при фиксированном `k` блоки `B[k][0..N-1]` лежат в памяти **подряд** — чтение B
  последовательное;
* блок `A[i][k]` переиспользуется для всей строки блоков C;
* строка блоков `C[i][*]` остаётся в кэше на всём цикле по `k`.

**Транспонирование матриц не используется** — оно запрещено заданием.

### 2. Запрет свёртки в FMA: `-ffp-contract=off`

По умолчанию clang/GCC на `-O3` сворачивают `a*b + c` в одну инструкцию FMA
(`vfmadd...`), если целевой процессор её поддерживает. FMA округляет **один раз**
вместо двух, поэтому результат отличается в последних битах. Если бы
автовекторизованная версия получила FMA, а SSE2-версия (в SSE2 инструкции FMA нет)
не получила, C1 и C2 перестали бы совпадать.

Поэтому:

* весь проект собирается с `-ffp-contract=off`;
* в ручной версии используются раздельные `_mm_mul_pd` и `_mm_add_pd`.

`-ffast-math` не используется нигде: он разрешил бы компилятору переставлять слагаемые
и тем самым сломал бы совпадение.

## Как отключена автовекторизация

Только **ключами компилятора**. Файл `src/multiply_scalar.cpp` компилируется два раза
из одного и того же исходного текста (см. `Makefile`):

```make
# автовекторизация ВКЛЮЧЕНА
build/multiply_auto.o:  c++ -O3 -msse2 ... -DMUL_FN=multiply_auto  -c src/multiply_scalar.cpp

# автовекторизация ВЫКЛЮЧЕНА
build/multiply_novec.o: c++ -O3 -msse2 ... -fno-vectorize -fno-slp-vectorize \
                                           -DMUL_FN=multiply_novec -c src/multiply_scalar.cpp
```

Имя функции подставляется макросом `MUL_FN`, поэтому в одном исполняемом файле
оказываются обе версии. **Прагм, управляющих векторизацией, в исходниках нет вообще** —
это можно проверить:

```sh
make no-pragma-check
```

Makefile определяет компилятор и подставляет нужные ключи:

| Компилятор | Отключение векторизации |
|---|---|
| clang | `-fno-vectorize -fno-slp-vectorize` |
| GCC | `-fno-tree-vectorize -fno-tree-slp-vectorize` |
| MSVC (если переносить проект) | `/Qvec-` при `/O2` |

## Доказательство векторизации

### Способ 1 (основной) — дизассемблер

```sh
make asm
```

Генерирует `build/*.s` и считает инструкции умножения/сложения `double`:

```
  Объектный файл                        векторных    скалярных
  ────────────────────────────────── ──────────── ────────────
  multiply_novec.s                              0          128
  multiply_auto.s                              64            0
  multiply_simd.s                             128            0
```

* **векторных** — `mulpd` / `addpd` (packed): две операции `double` за инструкцию;
* **скалярных** — `mulsd` / `addsd` (scalar): одна операция за инструкцию.

В версии с `-fno-vectorize -fno-slp-vectorize` векторных инструкций **ровно ноль**,
а в двух остальных — ровно ноль скалярных.

### Способ 2 — отчёт компилятора

```sh
make vecreport
```

Собирает с `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize
-Rpass-analysis=loop-vectorize` (для GCC — `-fopt-info-vec`). В невекторизованной
сборке компилятор сообщает `loop not vectorized`. В векторизованной замечание
относится к *циклическому* векторизатору: внутренний цикл по `c` имеет константное
число итераций (8), поэтому компилятор сначала разворачивает его целиком, а
векторизацию выполняет уже **SLP-векторизатор**, который отдельного замечания
«vectorized» не печатает. Именно поэтому основным доказательством служит дизассемблер.

## Ручная векторизация SSE2

`src/multiply_simd.cpp`, `<emmintrin.h>`:

| Операция | Интринсик |
|---|---|
| тип вектора | `__m128d` (регистр `xmm`, 128 бит = 2 × `double`) |
| загрузка / выгрузка | `_mm_load_pd` / `_mm_store_pd` |
| размножить скаляр | `_mm_set1_pd` |
| умножение | `_mm_mul_pd` |
| сложение | `_mm_add_pd` |

### За счёт чего ручная версия быстрее автоматической

Автовекторизатор обрабатывает строку блока C по одной. Ручное ядро (`accumulate<Rows>`)
обрабатывает **две строки блока сразу**:

* вдвое больше независимых цепочек сложений, поэтому скрывается латентность `addpd`
  (накопление в один аккумулятор — строго последовательная цепочка);
* каждая строка B загружается один раз и используется для двух строк C.

Строки блока независимы, поэтому их обработка вперемежку **не меняет порядок
слагаемых ни для одного элемента** — побитовое совпадение с C1 сохраняется.

Шаг по строкам выбирается на этапе компиляции (`kRowStep`) исходя из того, поместятся
ли аккумуляторы в 16 регистров `xmm`: для блока `8×8` это 2 строки × 4 вектора = 8
аккумуляторов, для крупных блоков ядро автоматически переходит на одну строку, чтобы
не вызвать выгрузку регистров в память. Нечётный размер блока обрабатывается
хвостовым скалярным столбцом.

## Универсальность (бонусное условие)

* размеры внешних матриц произвольные и задаются во время выполнения:
  `./build/lab1 --size 200,256,300`;
* размер малой матрицы задаётся при сборке: `make BLK=5` — в том числе **нечётный**,
  для него SIMD-ядро обрабатывает хвостовой столбец скалярно;
* проверено на `BLK = 3, 5, 8, 12, 16, 32` и на неквадратных внешних размерах — во всех
  случаях C1 и C2 совпадают побитово.

## Команды

| Команда | Что делает |
|---|---|
| `make` | сборка в `build/` (Release: `-O3 -DNDEBUG -ffp-contract=off -msse2`) |
| `make run` | сборка и запуск с настройками по умолчанию |
| `make bench` | прогон в три повтора |
| `make check` | быстрая проверка совпадения C1 и C2 на малом размере |
| `make asm` | ассемблерный листинг и подсчёт векторных инструкций |
| `make vecreport` | отчёт компилятора о векторизации циклов |
| `make no-pragma-check` | убедиться, что прагм векторизации в коде нет |
| `make clean` | удалить `build/` |

Переменные: `SIZE=<L или L,M,N>`, `REPEAT=<N>`, `BLK=<N>`, `ARGS='<флаги программы>'`,
`EXTRA='<доп. флаги компилятора>'`.

```sh
make run SIZE=320 REPEAT=3
make run ARGS='--skip-novec'
make BLK=5 && ./build/lab1 --size 40,55,37
./build/lab1 --help
```

Программа возвращает код `0`, если результаты всех версий совпали побитово, `1` —
если нет, `2` — при ошибке в аргументах.

**Вывод фрагментов матриц не делается** — это запрещено заданием; печатаются только
параметры запуска, замеры и вердикт о совпадении плюс одна контрольная сумма.

## Замечание про Mac на Apple Silicon

Проект рассчитан на x86-64 и на ARM-маке штатно не соберётся (SSE2 там нет).
Для проверки на Apple Silicon можно собрать x86-64-бинарник и запустить его
через Rosetta 2:

```sh
make EXTRA="-arch x86_64" && ./build/lab1 --size 64
```

Результаты и совпадение C1/C2 при этом корректны, но замеры времени показывают
скорость трансляции Rosetta, а не реального процессора — за цифрами
производительности нужно идти на настоящую x86-машину.
