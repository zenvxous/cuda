# Лабораторная работа №2 — оптимизация умножения матриц под кэш

**Тип `double`, ручная векторизация NEON, плотные матрицы. Платформа: arm64 (Apple M2).**

Продолжение лаб.1: взята **только векторизованная** версия, «матрица матриц» удалена
(как разрешает задание), и к ней применена оптимизация доступа в кэш.

```sh
make          # сборка (Release)
make run      # основной прогон
make probe    # профиль иерархии кэша
make help     # все цели
```

## Версии алгоритма

| Ключ | Версия | Что это |
|---|---|---|
| `c1` | **C1** векторизованная, без оптимизации кэша | порядок `i-j-k`, **эталон** для проверки совпадения |
| `c2` | **C2** блочная по заданию | `blocksize = LLC/3 · 0,9`, ширина кратна 64 Б |
| `c3` | **C3** по всей иерархии кэша | вложенный тайлинг: LLC → L1d → регистры |
| `naive` | **C0** скалярная `i-j-k` | опорная, без векторизации (`--with-naive`) |
| `ikj` | **C1a** перестановка циклов на `i-k-j` | диагностика (`--diag`) |
| `reg` | **C1′** регистровая блокировка без кэш-блокировки | диагностика (`--diag`) |
| `blk0` | **C2′** кэш-блокировка с ядром C1a | диагностика (`--diag`) |

Все версии обязаны совпадать с C1 **побитово** — программа это проверяет.

## Что такое C1 и почему она медленная

C1 — это умножение, записанное **в исходном порядке циклов `i-j-k`** и
векторизованное вручную теми же пятью интринсиками, что и в лаб.1. Именно так задача
пишется до того, как начинаешь думать о кэше.

```cpp
for (int i = 0; i < m; ++i) {
  for (int j = 0; j + 2 <= n; j += 2) {
    float64x2_t acc = vdupq_n_f64(0.0);
    for (int k = 0; k < k_size; ++k) {
      const float64x2_t a_vec = vdupq_n_f64(a_row[k]);
      acc = vaddq_f64(acc, vmulq_f64(a_vec, vld1q_f64(b_row_k + j)));
    }
    vst1q_f64(c_row + j, acc);
  }
}
```

Векторизация здесь настоящая: два `double` за инструкцию, аккумулятор в регистре.
Проблема не в арифметике, а в доступе к B.

Внутренний цикл идёт **по столбцу B**: адреса `B[0][j]`, `B[1][j]`, `B[2][j]`… отстоят
друг от друга на длину строки — при N = 2560 это 20 КБ. Каждое обращение падает
в новую линию кэша, из её 128 байт используются 16 — **утилизация линии 12,5 %**,
остальное подтянуто зря и будет вытеснено до того, как понадобится.

Отсюда и результат: 1,71 GFLOP/s против 21,66 у блочной версии.

## Откуда берутся 12,7×

Разложение по шагам — это и есть содержательная часть работы:

| Шаг | Время, с | Прирост | Что сделано |
|---|---|---|---|
| C1 исходная | 19,649 | — | порядок `i-j-k`, вектор по `j` |
| C1a | 2,605 | **7,54×** | перестановка циклов на `i-k-j` |
| C2 | 1,549 | **ещё 1,68×** | кэш-блокировка + регистровая блокировка |
| | | **итого 12,7×** | |

### Шаг 1: перестановка циклов — 7,54×

Меняем местами циклы по `j` и `k`. Теперь внутренний цикл идёт по **строке** B,
элементы лежат подряд, линия кэша используется на все 100 %, и подключается
аппаратный префетчер. Формально это **loop interchange** — первая и самая дешёвая
оптимизация доступа в кэш.

Порядок слагаемых при этом не меняется: для каждого элемента C сумма по-прежнему
набирается по возрастанию `k`. Поэтому результат совпадает с C1 побитово.

### Шаг 2: блокировка — ещё 1,68×

И вот тут выясняется, что **ни кэш-блокировка, ни регистровая блокировка не работают
поодиночке**. Относительно C1a:

```
C2′  только кэш-блокировка       0.96×   ничего
C1′  только регистровая          0.36×   втрое хуже
C2   обе вместе                  1.68×
```

**Почему кэш-блокировка сама по себе бесполезна.** После перестановки циклов C1a
уже не упирается в память: 62,6 ГБ за 2,6 с — это 26 ГБ/с, а M2 умеет заметно больше,
и доступ к B последователен, то есть идеален для префетчера. Настоящее узкое место
C1a — **обращения к матрице C в L1**: при накоплении в памяти на каждом шаге по `k`
идёт загрузка C, умножение, сложение и запись C, то есть два обращения к L1 на две
арифметические операции.

**Лечение — регистровая блокировка.** Микроядро `kernel_reg` (`include/kernel.hpp`)
держит блок C размером `4 × 8` в 16 векторных регистрах (в AArch64 их 32) и прогоняет
по нему весь цикл `k`, обращаясь к C ровно один раз на входе и один раз на выходе.
Спиллов нет:

```sh
grep -cE 'str[[:space:]]+q[0-9]+, \[sp' build/mul_block.s   # 0
```

**Но регистровая блокировка требует кэш-блокировки.** Держать C в регистрах через
весь цикл `k` можно только если для фиксированного столбцового блока пройти все `k` —
а это снова делает доступ к B шаговым. Без кэш-блокировки шаг идёт по всей матрице B
размером 52 МБ, мимо L2 — отсюда провал C1′ до 0,36×.

Тайл 784×784 (6,1 МБ) резидентен в L2, шаговый доступ внутри него бесплатен, и обе
оптимизации наконец складываются: 21,66 GFLOP/s против 12,88 у C1a.

## Обоснование преимуществ: три независимых аргумента

### 1. Цена промаха, измеренная на этой машине

```sh
make probe
```

Pointer chasing по случайной перестановке с шагом в линию кэша, свип размера рабочего
множества. Часы — `std::chrono::high_resolution_clock`.

```
  Рабочее множество   нс/доступ
     128.00 КБ      1.07    [= L1d]
     256.00 КБ      6.22  ███  ← ступень
       8.00 МБ      8.94  ████  ← ступень
      16.00 МБ     21.88  █████████  ← ступень  [= L2]
      32.00 МБ     88.37  ██████████████████████████████████████  ← ступень
     512.00 МБ    108.30  ██████████████████████████████████████████████
```

Ступени точно совпадают с `sysctl`: L1d 128 КБ, L2 16 МБ. **1,07 нс из L1 против
108 нс из памяти — сто раз.** Отсюда правило выбора размера блока: три блока
(A, B, C) должны оставаться левее ступени 16 МБ.

### 2. Аналитическая модель трафика

Сколько раз алгоритм целиком перечитывает матрицу:

```
│ Версия                                 │ проходов A │ проходов B │ обращ. C │    объём │
├────────────────────────────────────────┼────────────┼────────────┼──────────┼──────────┤
│ C1  векторизованная, i-j-k             │          1 │       2560 │        1 │ 125.1 ГБ │
│ C1a перестановка на i-k-j              │          1 │       1280 │        2 │  62.6 ГБ │
│ C2  блочная по заданию                 │          4 │          4 │        8 │ 800.0 МБ │
```

Блокировка сокращает объём чтений в **156 раз** относительно C1.

### 3. Замер

12,7× на матрицах 2560×2560 при побитовом совпадении результатов.

## Размер блока: формула задания

```
blocksize = LLC / 3 · 0,9              максимальный размер ОДНОГО блока
T         = ⌊ √(blocksize / 8) / 16 ⌋ · 16      сторона квадратного тайла
```

Делитель 3 — потому что в кэше одновременно должны жить блоки **трёх** матриц
(A, B и C), множитель 0,9 — запас на всё остальное, что вытесняет наши данные.

Распределение `blocksize` по X и Y задание оставляет на наше усмотрение — выбран
**квадратный** тайл: он минимизирует объём подтягиваемых данных при фиксированной
площади и даёт одинаковое число проходов по A и по B.

На M2: `blocksize = 16 МБ / 3 · 0,9 = 4,80 МБ`, `T = 784`.

### Требование кратности 64 байтам

```
T = 784 элемента → 784 · 8 = 6272 байта = 98 линий по 64 Б → кратно 64 ✓
```

На M2 линия кэша **128 байт**, а не 64 (`sysctl hw.cachelinesize`), поэтому
выравнивание идёт на 16 элементов = 128 байт — требование задания выполняется
с запасом. Дополнительно шаг строки матрицы (`stride`) округляется вверх до кратного
16 элементам, а базовый адрес выровнен на 128 байт (`posix_memalign`). Поэтому
**каждая строка каждого блока начинается с границы линии кэша**.

### Порядок обхода блоков

Задание требует: блок одной матрицы остаётся неизменным, пока не обработаны ВСЕ блоки
второй. Реализовано в `src/mul_block.cpp`:

```
для ii   (полосы строк C)
  для kk (полосы по k)          ← фиксируем блок A[ii][kk]
    для jj                      ← прогоняем ВСЕ блоки B этой полосы
      C[ii][jj] += A[ii][kk] · B[kk][jj]
```

---

## Что делать, когда L3 нет

`blocksize` считается от L3, но на Apple Silicon L3 отсутствует: `sysctl hw.l3cachesize`
не возвращает ничего. Есть L1d 128 КБ на ядро и **L2 16 МБ на кластер P-ядер**, а
системный кэш (SLC) через `sysctl` не виден.

За последний уровень берётся самый большой доступный кэш — на M2 это L2, который там
и играет роль L3. В отчёте всегда печатается, какой именно кэш взят и почему:

```
  L3 ..................... отсутствует (Apple Silicon)
  LLC для формулы ........ 16.00 МБ — L2 (L3 отсутствует)
```

Любой уровень переопределяется флагом: `--llc`, `--l2`, `--l1`, `--line`.

## C3: блокировка по всей иерархии кэша

`src/mul_block_multi.cpp` строит список уровней **из фактически обнаруженной
иерархии** и рекурсивно вкладывает тайлы, считая сторону для каждого уровня по той же
формуле. На M2 получается два уровня плюс регистровое микроядро:

| Уровень | Размер | Бюджет блока | Сторона тайла |
|---|---|---|---|
| L2 (он же LLC) | 16,00 МБ | 4,80 МБ | T = 784 |
| L1d | 128,00 КБ | 38,4 КБ | T = 64 |
| регистры `v` | 32 × 128 бит | — | 4 × 8 |

Порядок `i-k-j` соблюдается на каждом уровне, поэтому побитовое совпадение сохраняется
при любом числе уровней.

При настройках по умолчанию C3 идёт наравне с C2 (1,542 против 1,549 с). Это честный
результат: внутри тайла 784×784 микроядро уже работает с L1-резидентным рабочим
множеством, поэтому отдельный уровень L1 добавляет только накладные расходы на циклы.

Зато многоуровневость даёт **устойчивость к неверно выбранному размеру тайла**. Если
внешний тайл заведомо велик (LLC задан как 128 МБ, T = 2240, в L2 такой тайл не лезет):

```sh
./build/lab2 --size 2560 --llc 128M --only c2,c3
```
```
│ C2  блочная по заданию   │ 5.801 с │  5.78 GFLOP/s │
│ C3  по всей иерархии     │ 1.484 с │ 22.61 GFLOP/s │
```

Одноуровневая версия проваливается в **3,9 раза**, многоуровневая держит скорость:
внутренние уровни сами доводят рабочее множество до размера кэша.

## Почему все версии совпадают ПОБИТОВО

Требование задания — C1 и C2 должны совпадать **полностью**. Для `double` это значит
побитово, а такое возможно только при одинаковом порядке операций с плавающей точкой.

**1. Во всех версиях сумма для каждого элемента набирается в порядке возрастания `k`.**

| Версия | Почему `k` монотонен |
|---|---|
| C0, C1 | `k` — внутренний цикл, идёт подряд |
| C1a, C1′ | перестановка циклов меняет порядок обхода, но для каждого отдельного элемента `k` по-прежнему возрастает |
| C2, C3 | внешний цикл по блокам `kk` возрастает, внутри тайла `k` возрастает → глобальный `k` монотонен |

Разворот по `i` (микроядро считает 4 строки сразу) порядок не меняет: разные строки
результата независимы.

**2. `-ffp-contract=off` на весь проект.** Иначе компилятор свернёт `a*b + c` в `fmla`,
которая округляет один раз вместо двух, и версии разойдутся в последних битах. В ручном
коде по той же причине раздельные `vmulq_f64` и `vaddq_f64`, а не `vfmaq_f64`.

**3. `-ffast-math` не используется нигде** — он разрешил бы переставлять слагаемые.

Проверка: `memcmp` каждого результата с C1 по всем строкам плюс максимальная
абсолютная разница и число различающихся элементов.

Любопытная деталь для защиты: в скалярной опорной версии компилятор всё же
векторизовал **умножения** (`fmul.2d`), но сложения оставил скалярными, извлекая
половины регистра (`mov d5, v1[1]`) — переставлять слагаемые ему нельзя.
Видно в `make asm`.

## Измерение времени

`clock()` и `time()` не вызываются нигде в проекте.

| Что | Чем |
|---|---|
| время | `std::chrono::high_resolution_clock` |
| такты | `mrs cntvct_el0` — аналог `__rdtsc()` на arm64 |

На Apple Silicon `cntvct_el0` — **системный таймер** (частота из `cntfrq_el0`, на M2
24 МГц), а не счётчик тактов ядра: `PMCCNTR_EL0` из пользовательского режима
недоступен. Поэтому столбец подписан «Такты», без выдачи за частоту ядра.
