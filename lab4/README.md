# Лабораторная работа №4 — базовые алгоритмы CUDA (reduce)

**Задание 10. Взвешенное среднее балла по массивам оценок и весов `float` с использованием reduce.**

$$\bar{x}_w = \frac{\sum_{i=1}^{N} w_i x_i}{\sum_{i=1}^{N} w_i},\qquad N \in [10, 10^6],\quad w_i > 0$$

Обе суммы считаются **за один проход** одной свёрткой: элемент свёртки — пара
`Pair{wx, w}`, операция — покомпонентное сложение. Деление делается один раз в конце.
Отдельно `Σwx` и `Σw` двумя проходами считать незачем: массивы пришлось бы читать дважды,
а задача упирается в память.

| Параметр | Ключ | Допустимые значения | По умолчанию |
|---|---|---|---|
| размер массивов `N` | `--n N` | `[10, 1 000 000]` | `1 000 000` |
| зерно генератора | `--seed S` | `≥ 0` | `2026` |
| число замеров | `--repeat R` | `≥ 1` | `20` |
| размер блока | `--block B` | степень двойки от 32 до 1024 | G1, G2 — 256; G3 — 128, 256, 512, 1024 |

Данные генерируются `std::mt19937`: оценки `x ∈ [0, 100]`, веса `w ∈ [0.01, 10]`;
положительность весов проверяется. Значения вне диапазонов программа отвергает с
сообщением об ошибке.

```sh
make            # сборка (nvcc, Release: -O3)
make run        # основной прогон: N = 10^6
make quick      # N = 10^5
make ptx        # PTX ядер: проверить, что FMA не появилось
make help
```

Если `nvcc` старше 11.6 и не знает `-arch=native`, архитектуру надо указать явно:
`make ARCH=sm_75` (Turing), `sm_86` (Ampere, RTX 30xx), `sm_89` (Ada, RTX 40xx).
Ключи программы передаются через `ARGS`: `make run ARGS="--n 1000 --block 128"`.

---

## Что делает программа

1. Генерирует `x` и `w` в pinned-памяти хоста и считает **точный ответ в `double`**
   (`weighted_mean_exact`): произведение двух `float` в `double` точное, а погрешность
   суммы в `double` на 10⁶ слагаемых — около 10⁻¹⁰, на семь порядков ниже `float`.
2. Замеряет **CPU в один поток** — обычный цикл `acc += w[i]·x[i]` во `float`
   (`reduce_sequential`), через `std::chrono::high_resolution_clock`.
3. Копирует `x`, `w` на GPU и отдельно замеряет копирование.
4. Прогоняет четыре GPU-версии (устройство — ниже): **G1**, **G2**, **G3** с несколькими
   размерами блока и **CUB** `DeviceReduce::Reduce` в качестве библиотечной планки.
5. Каждая версия: прогрев, затем `--repeat` замеров через `cudaEvent`. Перед каждым
   замером **вытесняется L2** — `cudaMemsetAsync` буфера размером 2×L2. Иначе 8 МБ
   данных остаются в L2 (на Ampere/Ada это 6–72 МБ), и полоса в таблице оказывается
   полосой L2, а не видеопамяти.
6. Результат каждой версии **сверяется**: G1–G3 — побитово с CPU-эмуляцией той же
   схемы, CUB — с `double` по относительной ошибке `≤ 10⁻⁵`. При расхождении
   программа завершается с кодом 1.

В таблице: лучшее и среднее время, эффективная полоса `8N байт / время`, ускорение к CPU,
относительная ошибка `x̄_w` к точному ответу и итог сверки.

## Устройство reduce

Все схемы — дерево: на каждом шаге половина «живых» элементов прибавляет к себе
вторую половину, `log₂ B` шагов на блок из `B` потоков. Между уровнями нужен
`__syncthreads()`. Блок сворачивает свой кусок в одну пару и пишет её в глобальную
память, частичные суммы блоков сворачиваются следующим запуском того же ядра. Слить
всё в один запуск через `atomicAdd` для `float` можно, но тогда результат зависит
от порядка прихода блоков и меняется от запуска к запуску. Поэтому atomics нет,
а уровни идут отдельными запусками.

**G1 — interleaved addressing** (Harris, *Optimizing Parallel Reduction in CUDA*, шаг 1):

```cpp
for (unsigned s = 1; s < blockDim.x; s *= 2) {
  if (tid % (2 * s) == 0) sh[tid] = combine(sh[tid], sh[tid + s]);
  __syncthreads();
}
```

Работают потоки 0, 2, 4…, потом 0, 4, 8… — активные потоки разбросаны по всем варпам,
поэтому **каждый варп расходится** (warp divergence) и выполняет обе ветки. Ни один варп
не освобождается до последних шагов. Плюс медленный `%` и конфликты банков shared-памяти
при шаге `2s·8` байт. Число уровней — `⌈log_B N⌉`: при `N = 10⁶`, `B = 256` это 3 запуска
(3907 → 16 → 1).

**G2 — sequential addressing** (Harris, шаг 3):

```cpp
for (unsigned s = blockDim.x / 2; s > 0; s >>= 1) {
  if (tid < s) sh[tid] = combine(sh[tid], sh[tid + s]);
  __syncthreads();
}
```

Работают потоки `0 … s−1`, подряд. Пока `s ≥ 32`, варпы либо целиком работают, либо
целиком простаивают — расхождения нет. Чтение подряд идущих адресов — без конфликтов
банков. Число запусков то же, что у G1.

**G3 — grid-stride + warp shuffle** (Harris, шаги 4–7 в современном виде):

- сетка фиксирована: `SM × (maxThreadsPerSM / B)` блоков — ровно столько, сколько
  помещается на GPU за раз, но не больше `⌈N/B⌉`;
- каждый поток сначала **накапливает в регистре** элементы `i, i + G·B, i + 2G·B, …`.
  Это последовательное чтение с объединением обращений (coalescing), и почти вся работа
  идёт без shared-памяти и `__syncthreads()`;
- дерево в shared-памяти идёт только до 32 элементов, последние 5 шагов делает один варп
  через `__shfl_down_sync` — обмен регистрами внутри варпа без shared-памяти и без
  синхронизации;
- всегда **ровно 2 запуска**: G частичных сумм, затем один блок сворачивает их.

**CUB** — `cub::DeviceReduce::Reduce` с той же операцией `Combine` и входом через
`thrust::transform_iterator`, который на лету делает из `(x[i], w[i])` пару `{w·x, w}`.
Временный буфер CUB выделяется один раз заранее и в замер не входит.

Общий код CPU и GPU — `include/wmean.cuh`, функции `__host__ __device__`:

```cpp
__host__ __device__ inline Pair make_term(float x, float w) { return Pair{w * x, w}; }
__host__ __device__ inline Pair combine(Pair a, Pair b) { return Pair{a.wx + b.wx, a.w + b.w}; }
```

## Почему результаты совпадают побитово

Сложение `float` коммутативно, но **не ассоциативно**: `(a + b) + c ≠ a + (b + c)` в
последнем бите. Поэтому сумма зависит от формы дерева, и у G1, G2 и G3 она разная, а у
последовательного CPU-цикла — тем более. Сравнивать GPU с `for`-циклом побитово нельзя.

Поэтому в `src/reference.cu` для каждой GPU-схемы есть **CPU-эмуляция той же формы
дерева**: те же уровни, тот же размер блока, те же нули в хвосте последнего блока, та же
сетка G3 и тот же порядок накопления в grid-stride цикле. Свёртка последних 32 элементов
через `__shfl_down_sync` — то же дерево, что и sequential addressing с `s = 16 … 1`:
поток `l` на шаге `off` прибавляет значение потока `l + off`. Если формы деревьев
одинаковы, одинаковы и последовательности операций IEEE-754, а значит и результат.

Как и в лаб. 3, единственное, что может это сломать, — **слияние `a·b + c` в FMA**. В G3
после встраивания `make_term` в цикл получается ровно `acc.wx + w·x`, и nvcc по умолчанию
сделает из этого `fma.rn.f32`. Поэтому `-fmad=false` для GPU (проверяется `make ptx`:
`fma.rn.f32 в PTX: 0`) и `-ffp-contract=off` для хоста. Собрать с FMA можно так:
`make clean && make FMAD=true` — тогда G3 разойдётся со своей эмуляцией.

Порядок сложений CUB не документирован и зависит от версии и архитектуры, поэтому CUB
сверяется с `double` по относительной ошибке.

Эмуляции проверены на Mac через заглушку `cuda_runtime.h`: они побитово совпадают с
пошаговой симуляцией ядра G3, включая семантику `__shfl_down_sync`, при
`N ∈ {10, 31, 1000, 1023, 1025, 4097, 10⁵, 10⁶}` и `B ∈ {32, 128, 256, 1024}`.

## Точность: дерево против цикла

Побочный, но важный результат. При последовательном суммировании ошибка округления растёт
как `O(N·ε)`: к концу `Σwx ≈ 2.5·10⁸`, шаг сетки `float` там — 16, а каждое слагаемое
порядка 250. У дерева каждое слагаемое проходит только `log₂ N ≈ 20` сложений, ошибка —
`O(log N·ε)`. Проверено на M2 (данные по умолчанию, `seed = 2026`):

| N | Цикл float | G1 (256) | G2 (256) | G3 (256) |
|---|---|---|---|---|
| 1 000 | 4.3·10⁻⁷ | 5.0·10⁻⁸ | 2.5·10⁻⁸ | 2.5·10⁻⁸ |
| 100 000 | 4.8·10⁻⁷ | 5.1·10⁻⁸ | 5.1·10⁻⁸ | 5.1·10⁻⁸ |
| 1 000 000 | **1.6·10⁻⁴** | 1.1·10⁻⁷ | 1.1·10⁻⁷ | 4.7·10⁻⁸ |

То есть параллельная свёртка здесь не только быстрее, но и **точнее последовательного
цикла на три порядка**. Сетка G3 на конкретной карте другая, поэтому её ошибка в таблице
программы может немного отличаться.

## Что показывают замеры

> Таблица заполняется на машине с NVIDIA GPU, на MacBook (Apple M2) CUDA нет.

```
GPU:        …
Память:     …
│ Версия                           │ Лучшее, мс │ Среднее, мс │    ГБ/с │  vs CPU │ Отн. ош. │       Сверка │
├──────────────────────────────────┼────────────┼─────────────┼─────────┼─────────┼──────────┼──────────────┤
│ CPU, 1 поток, float подряд       │            │             │         │         │          │            — │
│ G1 interleaved, 256              │            │             │         │         │          │     побитово │
│ G2 sequential, 256               │            │             │         │         │          │     побитово │
│ G3 grid-stride+shfl, 128×…       │            │             │         │         │          │     побитово │
│ G3 grid-stride+shfl, 256×…       │            │             │         │         │          │     побитово │
│ G3 grid-stride+shfl, 512×…       │            │             │         │         │          │     побитово │
│ G3 grid-stride+shfl, 1024×…      │            │             │         │         │          │     побитово │
│ CUB DeviceReduce                 │            │             │         │         │          │       ≤ 1e-5 │
```

Чего ожидать и как объяснять:

- **Задача упирается в память, а не в арифметику**: на 8 байт чтения приходится одно
  умножение и два сложения. Мерилом служит не FLOP/s, а **эффективная полоса** в
  сравнении с пиковой, которую программа печатает в шапке. Хорошая свёртка выходит
  на 70–90 % пика.
- **При N = 10⁶ данных всего 8 МБ**, это 10–20 мкс чтения на современной карте. Время
  того же порядка уходит на сами **запуски ядер** (по несколько мкс). Поэтому G3 с двумя
  запусками выигрывает у G1/G2 с тремя не только за счёт ядра, но и за счёт числа
  запусков. До пика полосы при таком `N` не дойдёт никто, включая CUB. Чтобы увидеть
  предельную полосу, нужен размер побольше, но задание ограничивает `N ≤ 10⁶`.
- **G1 → G2**: заметный выигрыш на первом уровне. В G1 расходятся все варпы, в G2
  расхождение есть только на последних 5 шагах. G1 к тому же платит за `%` и конфликты
  банков.
- **G2 → G3**: в G2 каждый поток читает **один** элемент и тут же проходит дерево из
  `log₂ B` шагов с `__syncthreads()`, то есть на одну пару загрузок приходится 8 барьеров
  (при `B = 256`). В G3 поток читает сотни элементов подряд, а дерево проходится один раз
  на блок, так что накладные расходы размазаны.
- **Размер блока в G3** влияет слабо: сетка подстраивается так, что потоков на GPU всегда
  столько же. Маленький блок даёт больше частичных сумм для второго запуска, большой —
  более длинное дерево. Разница — единицы процентов.
- **CUB** — ориентир «как сделали бы в продакшене». G3 должна быть с ним наравне.
- **GPU против CPU**. CPU-цикл строгий: без `-ffast-math` компилятор не может
  переупорядочить сложения, векторизации нет, и цикл упирается в задержку цепочки
  сложений. GPU по ядру быстрее на порядки, но **копирование 8 МБ по PCIe** (единицы
  ГБ/с — десятки ГБ/с) занимает больше, чем сама свёртка. Программа печатает время лучшей
  версии **с копированием**, и честный вывод такой: ради одной свёртки данные на GPU
  перекладывать невыгодно. Свёртка на GPU оправдана, когда данные там уже лежат —
  например, это невязка итерационного метода, который весь считается на GPU.
